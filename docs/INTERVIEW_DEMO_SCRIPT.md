# 面试演示脚本（3–5 分钟）

## 30 秒：问题与产品定位

“企业支持的难点不是生成一段答案，而是让答案建立在制度和系统事实之上，并且让高风险动作可控。这个作品把一次 ERP 故障诊断拆成可观察的 Agent 工作流。”

首页打开后不需要立即运行。先切换右侧“执行轨迹 / 工具调用 / 知识来源”，强调默认展示的是脱敏运行快照，目的是让面试官第一眼就能看到产品深度，而不是空面板。

## 90 秒：执行与证据链

选择“公司范围 500”并开始诊断。随着进度推进，解释六个节点：问题理解、知识检索、工具规划、只读查询、证据校验和答案生成。

打开 `execute_tools`，说明前端只展示安全的输入/输出和审计摘要，不展示模型私有推理。再打开工具详情，指出 REST 边界、200 状态、延迟、零重试与 `side_effect: false`。打开知识来源，说明当前 lexical/vector 模式、检索分数和 citation validation 如何支持最终结论。

## 60 秒：Human-in-the-loop

诊断完成后点击“创建工单”。说明写操作在 `create_ticket` 前被确定性策略暂停：拒绝时 Mock ERP 不收到写请求；确认时才继续，并使用 `run_id` 作为幂等键。核心观点是“LLM 可以提议，但不能自行承担业务责任”。

## 60 秒：工程取舍

打开“工程视图”，按四层架构说明：React Workbench、FastAPI Agent、RAG、Mock ERP。重点回答三个问题：

1. 为什么不直连 ERP 数据库：保留系统所有权、鉴权、契约和审计边界。
2. 为什么需要证据门：引用必须属于当次召回，工具证据不足时降低置信度或请求补充信息。
3. 为什么 fixture 仍然重要：招聘者无需密钥即可稳定体验完整路径，同时真实 API 可按同一结构替换。

## 可追问点

- 评测：54 条 ground truth 的100%结果是 deterministic baseline，不把它包装成生产模型准确率。
- 安全：默认只读；写操作需要 HITL；运行记录支持审计和复盘。
- 可演进性：通过 typed API/SSE 把事件流替换为真实 LangGraph 执行，UI 状态模型不需要重写。
- 失败策略：检索为空、工具超时或引用失效时，返回证据不足，而不是编造根因。
